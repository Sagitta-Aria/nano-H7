# 数字圆环约 2 FPS 现场诊断

2026-10-19，通过 NX 当前运行服务和同一张现场照片回放定位。

## 结论

主要瓶颈是 CPU 圆环几何检测，而非数字 OCR：仅回放静态照片、完全不运行
OCR，即可复现每帧约 0.37～0.46 秒的处理耗时。此证据可以解释现场低帧率，
不依赖对电源状态的推测。

现场屏幕显示 2.5 FPS、结果年龄 638 ms。屏幕的 FPS 是
`RecognitionMonitor.process()` 单次处理耗时的倒数，不是摄像头实测采集帧率。
相机报告的 30 FPS 也是设备属性，不能当作采集吞吐测量。

## 环境与复现

- 进程：`host.camera --worker /dev/video0 --width 1024 --height 768 --display --mjpeg`。
- 现场设置：圆环 `min_area=300`、`detect_width=960`、`nearby_distance=100`。
- 摄像头二和原上位机保持运行；测量包含现场 CPU 竞争。
- 通过现有相机服务拍摄一张照片，无第二个相机占用者，无运动命令。
- 现场证据和回放脚本位于 `localtmp/ring_perf_20261019/`。
- NX 回放调用现有 `analyze_ring_frame()`，OpenCV 线程数与现场一样设为 1。

## 测量

8 次带 cProfile 的检测中位数为 460 ms。累计 3.773 秒中：

| 阶段 | 累计时间 | 说明 |
| --- | ---: | --- |
| 边缘候选与环带验证 | 2.031 s | 内含边缘观测 1.297 s |
| 两路二值轮廓检测 | 0.854 s | 全局阈值与自适应阈值均逐帧处理 |
| 自适应阈值 | 0.324 s | 已包含在整体检测内 |
| 图像缩放 | 0.206 s | 已包含在整体检测内 |

8 帧共调用 2432 次 `fitEllipseAMS`，即约 304 次/帧。最小面积 300
让较多小轮廓进入候选检查。边缘路径在椭圆拟合后才应用拟合面积过滤，
所以只提高最小面积也不能消除全部拟合开销。

移除 profiler 后，同图各 10 次的中位数：

| 检测宽度 | 单帧耗时 | 检测吞吐倒数 | 原图圆心 |
| --- | ---: | ---: | --- |
| 960 | 365.8 ms | 2.73 FPS | (358,316)、(726,318) |
| 640 | 215.9 ms | 4.63 FPS | (359,316)、(727,317) |
| 480 | 146.5 ms | 6.83 FPS | 仅 (726,318)，漏检 |

这里的吞吐仅为静态图检测耗时倒数，不是完整实时链路 FPS。640 虽然保留
这张图的两个目标，但选择的环面积有变化；不能据一张图宣称 OCR 或所有距离下
的精度都不变。现场第三个圆环位于画面边缘，两条基准路径都未输出它。

将最小面积改为 50000 的诊断试验耗时约 194 ms，但当前两个目标均消失，
所以不能直接恢复该默认值作为修复。试验只修改回放内存参数。

启用实际 TensorRT 异步预览 OCR 后，12 次回放中位数约 383 ms；和纯圆环
检测相近，说明 GPU OCR 不是主要限制。该段回放最终没有形成已确认数字，
不代表数字识别准确率通过。

另一个仅在回放进程内进行的等价百分位计算优化试验，将 960 宽检测降至
322.5 ms，输出圆心和面积一致，但提升不足以解决整个问题，没有修改正式算法。

## 后续优化边界

应优先减少小轮廓重复拟合及边缘/二值双路径的重复计算，再用真实靶标回放
验证断环、同心环、实心圆拒绝、圆心与 OCR 裁剪。640 宽可作为折中方案，
但要补充不同距离和 OCR 的验证。480 宽及直接提高面积阈值已发现漏检，不采用。

此次完成诊断，未修改运行代码、保存参数、功耗模式或固件，也未重启服务。

## 后续修复与部署（用户授权优化后）

前述结论是诊断阶段的记录。后续已修改并部署视觉代码，最终检测宽度使用
**800**：640 在单张照片上较快，但轻微位移/曝光变化会使部分细环漏检，故没有采用。
原相机继续采集 1024×768，OCR 从原图裁剪，输出坐标仍为原图像素。

修复包括：

- 椭圆拟合等距抽取至多 128 点，原轮廓仍作面积和完整残差核验；提前排除无孔洞的
  二值轮廓，并使用等价的专用 90 分位计算减少 NumPy 调度开销。
- 保留边缘和二值两条检测路径，继续识别断环、小环并拒绝实心圆。
- OCR 内区增加径向环带检查，去掉未闭合的内圈；过滤相对主笔画很小的印刷碎屑。
- 低分细字使用少量归一化视图，至少两个视图均达到普通 0.6 阈值才采用新补偿结果。
  原有阈值与旧补偿路径保留，没有用位置或数字顺序猜答案。
- 一个后台任务处理同一帧的全部圆环，避免每圈轮流等待导致 0.6 秒投票过期。
  三次投票、丢失轨迹清除和过期任务丢弃保留。同心环层切换允许有限的面积变化，
  同时要求圆心接近，避免因为选到不同环层而不断重建轨迹。
- 本机屏幕为每个已确认数字显示位置与置信度，标题明确为 `OCR GPU`。

验证结果：

- Windows 与 NX Python 3.8 各 71 项相关测试通过；新增回归先复现了慢帧率投票、
  断内圈污染 OCR 和同心环层切换导致轨迹重置的问题。
- 13 张历史实拍难例保持预期输出；三种字体的 1/2/3、4/7/12 和空环通过。
- 现场图作 60 帧小幅位移和 ±5% 曝光扰动：热身后 45/45 帧同时显示确认的 1、2。
- 部署后实际屏幕连续采样 6 次：均显示 1、2；FPS 分别为
  3.9、4.2、4.0、3.9、4.7、4.2。数字 1 约 0.64～0.69，数字 2 约 1.00。
  这些是处理 FPS 的现场样本，不是相机采集帧率或长期性能保证。
- 现场摆位已经变化，因此上线前后屏幕不是完全同一输入；同图旧版/新版回放
  另有记录。升级没有修改功耗模式、模型权重或 STM32 固件。
- 额外负例发现 Triplex 字体小写 l 会识别成 1；使用同一裁剪直接对比旧、新 OCR，
  均返回 1、0.917939。这是原模型的已知字符混淆，未宣称字母负例全部通过。

NX 原视觉 OpenCV 4.9 没有 CUDA 支持；TensorRT OCR 正常使用 GPU。没有替换
现场 OpenCV/CUDA 环境，也没有宣称轮廓或椭圆拟合已迁移到 GPU。

关闭并重新打开摄像头一；上位机服务 PID 1794 保持，摄像头二继续运行，没有运动指令。

## 最终修复（2026-10-19）

上一版实际屏幕只有约 10～12 FPS，继续分段计时后发现还存在两个独立问题：

- UVC 驱动在 1024×768 MJPEG 下使用单个 V4L2 缓冲时，`grab()+retrieve()` 实测只有
  14.92 FPS；缓冲数为 2 时为 29.82 FPS。相机属性虽然一直返回 30 FPS，但单缓冲实际会隔帧等待。
- 局部圆环快速检测使用独立裁剪时，裁剪后的 Otsu 阈值和缩放采样相位会使细环偶发失败，
  进而重复触发整帧搜索。现在每帧先建立一张统一缩放图和全局阈值，局部区域复用它；
  全局断环搜索放到 `spawn` 进程，避免与当前帧处理争用 Python GIL。

最终部署将 USB 缓冲数改为 2，并保留 800 宽快速圆环路径。NX 上 94 项测试通过，
150 帧扰动回放热身后 110/110 帧同时确认数字 1、2。实机屏幕连续 6 次采样显示
12.4、19.2、18.5、17.5、18.3、18.6 FPS；识别结果保持 1、2，数字 2 置信度 1.00。
取图仍为 1024×768，未降低分辨率。OpenCV 几何检测继续运行在 CPU；OCR 的 TensorRT
推理使用 GPU，这是当前环境的 CUDA 能力边界。

## 色块模式切换检查（2026-10-19）

不调用圆环检测或 OCR；在 NX 1024×768 已保存照片上，80 次带 profiler
回放中位耗时 11.93 ms、P90 14.37 ms。这不是现场 FPS。

30 Hz 完成三帧，旧代码显示 3.75 FPS。现由识别线程在模式变化时清空两秒
窗口，仅统计当前模式，第一帧尚无帧间隔时显示 0。未修改 HSV、面积、
