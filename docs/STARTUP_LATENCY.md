# 按启动到第一段运动（v0.2.27）

用户反馈的是坐标巡航／整场任务按下启动后长时间不动。本次按这个入口单独复现，不把途中停留的结果当成启动优化结果。

## 根因与修改

旧版路线按应答逐条上传，但 `Console.tick()` 在上传期间继续投递 AXIS、SERVO、AUX、LIFT、FLOW 等调试查询。一次队列长度检查后可以连续追加十余条查询，下一条路线命令被排在它们后面；每一轮又固定等待 50 ms。串口 `read(256)` 对不足 256 字节的应答还会耗完 20 ms 读取超时。这些延迟沿几十条配置命令累积。

- `nav_pending` 现在也属于任务调度阶段，上传期间不追加无关调试查询。
- 后台遥测单独标记为低优先级；任务命令保持原顺序，STOP 仍取消旧队列并优先处理。
- 串口按已到达字节读取，无数据时只阻塞等首字节；同序号重试、分帧和应答匹配不变。
- 串口回复唤醒 Web 调度，提交命令唤醒串口线程。10 ms 超时仅用于服务定时器，不阻塞已收到的应答。页面快照限制为 10 Hz，先处理控制再更新页面。
- 单键启动准备在匹配 ACK 更新 ARM／导航状态后直接发下一条；连接时已恢复的控制参数不在启动时重复发送。
- 导航仍通过匹配 path/op 的完成查询确认完成，确认后立即推进；不把运动 ACK 当成到达。

## 启动对照

使用同一 `tools/benchmark_startup.py`，分别加载保存的 v0.2.26 上位机包和本次代码。设备连接已建立，使用默认五站路线；一组从普通巡航按钮开始计时，一组从单键整场入口开始计时。终点为模拟板首次有底盘轴活动。

| 入口 | v0.2.26 | v0.2.27 | 首次运动前串口指令数 |
|---|---:|---:|---:|
| 普通坐标巡航 | 11.984 s | 1.063 s | 464 → 56 |
| 单键整场任务 | 14.704 s | 1.078 s | 547 → 55 |

这些是 Windows 上的真实上位机线程／队列加模拟 UART 测量，不是实车耗时。模型按 115200 波特率、每字节 10 bit、读取超时 20 ms 计费，使用 SIM 航向；不包括 USB 调度、MCU 实际处理、H723 冷启动校准、相机冷启动或现场 CPU 负载。Windows 定时器粒度也会影响结果。详细命令时间线保存于本版发布目录的 `startup-*.json`。

```powershell
python tools/benchmark_startup.py --entry navigation
python tools/benchmark_startup.py --entry competition
python -m unittest tests.test_control_latency tests.test_control_latency_arm -v
```

## 另外处理的途中等待

比赛运行快照的 `dwell_ms` 为 0，磁盘调试参数保持原值。圆列取消写死的 3 秒停留，以及已确认停止后额外的 100 ms 图像等待，仍只接受完成后的新帧。转向在 STEP 输出已空闲、连续三个新航向样本落入容差后完成，取消额外 300 ms 时间门槛；旧样本、超大采样间隔、误差超限仍不能凑数。

舵机没有位置到达反馈，显式配置的机构稳定时间和用户任务中的 wait 动作继续按配置执行。速度、加速度、航向 P、容差、站点坐标和视觉参数没有为了提速而改写。

## 验证范围

本地 Keil ARM Compiler 5 + MicroLIB 构建、实际 ARM 镜像执行测试、上位机回归和临时 SIM 浏览器验证。新增检查覆盖上传时无调试查询、启动 ACK 直接推进、已恢复调参不重复、遥测优先级、STOP 清队列、分片串口应答和新航向样本确认。发布校验结果见 `validation_startup_20261018.json`。
